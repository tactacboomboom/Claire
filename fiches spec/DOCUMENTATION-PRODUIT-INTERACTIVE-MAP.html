🗺️ Vue d'Ensemble

Les 4 Documents Clés

MRD — Market Requirements Document Pourquoi + Pour qui ? | Marché, Problèmes, Opportunités
Audience: Marketing, Execs | Timeline: Stable (1+ année)
BRD — Business Requirements Document Business Case | Stratégie, Objectifs, Scope
Audience: PM, Execs | Timeline: Moyen (1-2 trim)
PRD — Product Requirements Document Quoi construire ? | Features, Workflows, UX
Audience: PM, UX, Dev | Timeline: Court (1-2 sprints)
SRD — Software Requirements Document Comment construire ? | Architecture, APIs, Data Model
Audience: Dev, Arch | Timeline: Court (live during coding)

Les 3 Socles Immuables

1. Cohérence d'Intention
Même idée à chaque niveau, juste plus détaillée. MRD→BRD→PRD→SRD→Code doivent tous dire la même chose.
2. Traçabilité Bidirectionnelle
✓ Vers le bas : Chaque requirement trace à une feature ✓ Vers le haut : Chaque feature trace à un objectif
3. Non-Redondance
Chaque document a un rôle unique. MRD ≠ BRD ≠ PRD ≠ SRD (responsabilités bien séparées)

⚡ Les 4 Ruptures Critiques

Rupture 1: MRD → BRD
Transition: Marché → Stratégie interne
Risque: BRD ignore ce que MRD a découvert
Validation: BRD adresse tous les problèmes du MRD (même réduit en scope)
Rupture 2: BRD → PRD
Transition: Objectifs business → Features créatives
Risque: Features "orphelines" sans lien au BRD
Validation: Chaque feature trace à un objectif BRD
Rupture 3: PRD → SRD
Transition: Features → Architecture technique
Risque: Trade-offs cachés, spec trop ambitieuse
Validation: Trade-offs explicites, perf targets mesurables
Rupture 4: SRD → Code
Transition: Spec → Réalité du code
Risque: Révélateur d'implicites, découvertes tardives
Validation: Architecture réaliste pour le timeframe donné

🎯 Les 5 Axes de Variation

Axe 1: Abstraction ↔ Concrétion
MRD très abstrait → SRD très concret
Axe 2: Business ↔ Technical
MRD/BRD langage métier → SRD langage technique
Axe 3: WHAT ↔ HOW
MRD/BRD/PRD répondent "WHAT" → SRD répond "HOW"
Axe 4: Large Scope ↔ Narrow Scope
MRD marché entier → SRD une feature
Axe 5: Timeline
MRD stable 1 an → SRD change pendant le coding

🔄 Workflow de Brainstorming: Phase par Phase

APERTURE (Leadership + Direction)
Durée: 15 min
Participants: Toi + Product Owner / Executive
Objectif: Établir le contexte, les enjeux, l'intention stratégique

Questions Clés

  • Quel est le problème réel qu'on adresse ? (data-based)
  • Qui le souffre le plus ? (segmentation)
  • À quelle fréquence ? (magnitude)
  • Quel coût si on ne résout pas ? (urgency)
  • Market size ? (est-ce que ça vaut la peine ?)

Artefact: PROJECT CHARTER

Contient:
  • Problem Statement (marché, segments, magnitude)
  • Vision (état futur désiré)
  • Stakeholders & Roles
  • Contraintes fondamentales
  • Success Criteria (fonctionnel, non-fonctionnel, adoption)
DISCOVERY + DEFINE (Problèmes + Scope)
Durée: 40-50 min brainstorm
Participants: Toi + PM + Execs (stakeholder alignment)
Objectif: Transformer les problèmes marché en objectifs business

Questions Clés

  • De tous les segments du MRD, lequel on vise ? (Scope reduction)
  • Quel est notre business case ? (Revenue, timeline, ROI)
  • Quels objectifs business mesurables ? (Rétention, ARPU, market share)
  • Stakeholder alignment: qui faut convaincre ?

Pont avec le MRD

MRD dit: "Les devs perdent 2h/day à chercher du code"
BRD doit dire: "Nous, on cible LEQUEL de ces devs ?
Python/JS only? France only? Startups only?"
INSIGHT: BRD réduit intentionnellement le scope du MRD (c'est normal)

Artefact: BRD (Business Requirements)

Contient:
  • Executive Summary
  • Business Objectives & Target Segments
  • Business Case (Revenue model, ROI)
  • Stakeholder Requirements (Sales, Finance, CS)
  • Phase 1 Scope Definition (In/Out)
DEFINE + DESIGN (Features + Workflows)
Durée: 50-60 min brainstorm
Participants: Toi + PM + UX Designer (creative choices)
Objectif: Transformer les objectifs business en features concrètes

Questions Clés

  • Pour chaque objectif BRD, quelles features le réalisent ?
  • Qui sont les personas utilisateur ? (Workflows différents par persona)
  • Pour chaque feature, quel est le user workflow ?
  • Quels acceptance criteria ? (testables, précis)

Pont avec le BRD

BRD dit: "Objectif: Augmenter rétention de 20%"
PRD doit dire: "Comment ? Via notifications ?
Via recommandations ? Via communauté ?
Nous choisissons : [Feature X, Y, Z]"
INSIGHT: PRD fait un CHOIX CRÉATIF que BRD ne détermine pas

Artefact: PRD (Product Requirements)

Contient:
  • Product Vision
  • Personas & Pain Points
  • User Stories & Acceptance Criteria
  • User Workflows (Detailed)
  • Out of Scope (Phase 2+)
DESIGN + REVIEW (Architecture + Implementation)
Durée: 50-60 min brainstorm
Participants: Toi + Tech Lead + Architect (technical choices)
Objectif: Transformer les features en architecture technique

Questions Clés

  • Quels composants ? (Frontend, Backend, Database)
  • Quel data model ? (Tables, relationships, constraints)
  • Quel API design ? (Endpoints, request/response, errors)
  • Quels non-functional targets ? (Performance, scalability, security)
  • Quels trade-offs conscients ? ("Nous choisissons X sur Y parce que...")

Pont avec le PRD

PRD dit: "Feature: Chercher snippets par langage"
SRD doit dire: "Techniquement, comment ?
Database: SQLite or PostgreSQL?
Index strategy: B-tree on language?
Query latency target: 500ms?"
INSIGHT: SRD fait des TRADE-OFFS TECHNIQUES

Artefact: SRD (Software Requirements)

Contient:
  • System Architecture & Components
  • Technology Choices & Trade-offs
  • Data Model (SQL schema)
  • API Specification (endpoints, requests, responses)
  • Security & Performance Targets
  • Deployment Plan
  • Known Limitations & Future Improvements

✓ Checklist de Cohérence Intégrale

Cohérence MRD ↔ BRD

  • ☐ Chaque problème MRD est adressé dans le BRD
  • ☐ BRD justifie pourquoi on réduit le scope du MRD (stratégie consciente)
  • ☐ Objectifs business du BRD tracent directement au problème du MRD

Cohérence BRD ↔ PRD

  • ☐ Chaque objectif business a au moins une feature PRD qui l'adresse
  • ☐ Aucune feature "orpheline" (cool mais non-justifiée)
  • ☐ User workflows du PRD réalisent les objectifs du BRD

Cohérence PRD ↔ SRD

  • ☐ Chaque feature PRD peut être implémentée via l'architecture SRD
  • ☐ Acceptance criteria du PRD sont techniquement testables
  • ☐ Performance/scalability targets du SRD sont cohérentes

Absence de Redondance

  • ☐ MRD ne parle pas de business case (c'est le BRD)
  • ☐ BRD ne spécifie pas des features (c'est le PRD)
  • ☐ PRD ne parle pas d'architecture (c'est le SRD)
  • ☐ SRD ne parle pas de code en détail (c'est pendant le coding)

Traçabilité Bidirectionnelle

  • ☐ Vers le bas: Chaque requirement SRD trace à un feature PRD
  • ☐ Vers le haut: Chaque feature PRD trace à un objectif BRD
  • ☐ Réciproquement: Chaque problème MRD est couvert par une feature PRD

Cas d'Usage

Pour commencer un nouveau projet:

  1. Remplis le MRD (15 min) → Valide avec execs
  2. Brainstorm BRD (30-40 min) → Valide avec stakeholders
  3. Brainstorm PRD (50 min) → Valide avec PM + UX
  4. Brainstorm SRD (50 min) → Valide avec architecture
  5. Checklist de cohérence (10 min) → Identifie gaps
  6. Coding session avec Claude Code (120+ min) → Implémente le SRD sans questions

Pour débugger un projet en difficulté:

"Le code ne matche pas le PRD" → Rupture 3 cassée (SRD flou) → Reviens à Architecture
"Le PRD ne matche pas les objectifs business" → Rupture 2 cassée (PRD mal defini) → Reviens à Features
"Features orphelines" → Rupture 2 cassée (PRD non-tracé au BRD) → Retrace
"Personne ne sait pourquoi on fait ça" → Rupture 1 cassée (BRD pas aligné au MRD) → Reclarifie intent

Concepts Clés

Dette d'Intention
Gap entre ce qu'on voulait faire (MRD) et ce qu'on a vraiment fait (Code). S'accumule à chaque rupture.
Révélateur d'Implicites
Le développeur découvre les choses que les specs ont oubliées. C'est un diagnostic, pas un blâme.
Entropie Informationnelle
L'ambiguïté diminue à chaque phase: MRD (très ambigu) → Code (zéro ambiguïté).
Feedback Loop
Code révèle que SRD était irréaliste → revoir SRD → revoir PRD → revoir BRD. Essentiel mais court.
